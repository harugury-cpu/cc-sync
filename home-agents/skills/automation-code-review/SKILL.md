# Automation Code Review

업무 자동화 코드를 PR 리뷰 대신 점검한다. 사용자가 개발자가 아니어도 “무엇에 의존하고, 어디가 깨지기 쉬우며, 무엇을 먼저 확인해야 하는지”를 이해할 수 있게 정리한다.

## 대상 범위

- Apps Script, Google Workspace/GWS 자동화 코드
- Apps Script HTML Service, HTML/CSS/JS 기반 내부 서비스
- Illustrator/Adobe 스크립트, ExtendScript, UXP, 디자인 파일 자동화
- Monday, Sheets, Drive, Gmail, Docs, 외부 API 연동 코드
- 파일명, 폴더, 템플릿, 레이어, 아트보드, 컬럼, 보드 구조에 의존하는 자동화

## 먼저 확인할 것

- 어떤 스크립트/함수/트리거/HTML 화면이 대상인지 확인한다.
- 연결된 시트, 문서, 폴더, 보드, API, Illustrator 파일, 템플릿을 식별한다.
- 최근 문제 증상이나 구두 제보가 있으면 `automation-ops-triage` 형식으로 먼저 정리한다.
- 수정 요청이면 실행 전에 `task-gate`와 `automation-change-safety`를 적용한다.

## 리뷰 체크리스트

### 의존성

- 시트명, 탭명, 컬럼명, 컬럼 번호가 하드코딩되어 있는가?
- 파일명, 폴더명, 템플릿명, 레이어명, 아트보드명이 하드코딩되어 있는가?
- Monday 보드 ID, 그룹 ID, 컬럼 ID가 코드에 박혀 있는가?
- 날짜/시간대 기준이 명확한가?
- 트리거 실행, 버튼 클릭, 수동 실행이 충돌하지 않는가?
- 권한이나 API 토큰이 어디서 주입되는가?

### 결과물 위험

- 같은 데이터, 파일, 아트워크가 두 번 생성될 수 있는가?
- 빈 값, 삭제된 컬럼, 바뀐 레이어, 누락된 템플릿을 만나면 어떻게 되는가?
- 실패 중간에 일부만 저장될 수 있는가?
- 재실행하면 안전한가?
- 운영 데이터/원본 파일에 바로 쓰기 전에 테스트 사본으로 확인 가능한가?

### 유지보수성

- 함수 이름만 보고 역할이 보이는가?
- 설정값과 처리 로직이 분리되어 있는가?
- 에러 로그가 충분한가?
- 사용자가 봐야 할 운영 설명이 코드 밖에 정리되어 있는가?

## 출력 형식

```markdown
## 결론
- 이 자동화는 [안정/주의/위험] 상태입니다.

## 한 줄 설명
- 이 자동화가 무엇을 하는지 비개발자 기준으로 설명.

## 의존성 지도
- 입력:
- 처리:
- 출력:
- 외부 연결:

## 위험요소
1. ...

## 먼저 볼 부분
1. ...

## 수정 전 확인
- automation-change-safety로 넘겨야 할 항목:
```
