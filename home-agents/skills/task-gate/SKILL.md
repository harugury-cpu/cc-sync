# Task Gate

사용자가 어떤 일을 시켰을 때 바로 실행하지 않고, 먼저 작업의 성공 기준과 실패 가능성을 명확히 고정하는 공통 운영 규칙이다.

## 적용 대상

다음 요청에는 반드시 적용한다.

- 코드 수정/구현/리팩터링
- 파일 생성/수정/삭제/이동
- 스케줄 등록/수정/삭제
- Claude/Codex 스킬 변경
- Obsidian 기록 자동화 변경
- 메모리 인프라, LanceDB, Wiki, Graphify, dump, wrap-up 변경
- 봇/훅/CLI/환경 설정 변경
- 사용자가 "되게 해줘", "고쳐줘", "수정해줘", "등록해줘", "연동해줘", "자동화해줘"라고 요청한 작업

단순 설명, 요약, 읽기, 상태 확인만 요청한 경우에는 생략해도 된다.

## 착수 전 필수 출력

작업을 실행하기 전에 아래 3가지를 먼저 제시한다.

```markdown
## 완료조건
- 무엇이 되어야 완료인지
- 기존에 깨지면 안 되는 것
- 사용자가 기대하는 최종 상태

## 실패케이스
- 트리거가 안 걸리는 경우
- 잘못된 대상에 적용되는 경우
- 중복/누락/권한/경로/동기화 문제
- 환경 차이로 재현되지 않는 경우
- 사용자가 알아차리기 어려운 조용한 실패

## 검증방법
- 실행할 명령
- 확인할 파일/경로/로그
- 성공으로 볼 출력
- 실패 시 복구 방법
```

사용자가 이미 명확히 "진행", "응", "해줘"로 승인한 경우에는 실행해도 된다.

## 작업 후 필수 보고

완료를 주장하기 전에 검증을 실행하고 결과를 보고한다.

```markdown
## 검증결과
- 실행 명령:
- 결과:
- 통과:
- 실패/주의:
```

코드나 자동화 변경의 경우 테스트/빌드/조회 명령을 실제로 실행한다. 테스트가 없으면 파일 존재, 설정 반영, CLI 조회, 로그 확인 등 수동 검증 결과를 남긴다.

## 실패 모드 사고법

아래 질문으로 엣지케이스를 뽑는다.

1. 이 작업이 아예 실행되지 않으면 어떻게 알 수 있나?
2. 잘못된 대상에 적용되면 어떻게 알 수 있나?
3. 일부만 성공하면 어떤 증상이 나오나?
4. 중복 실행되면 문제가 생기나?
5. 다른 봇/세션/환경에서는 다르게 동작하나?
6. 사용자가 보기에는 성공처럼 보이지만 실제로 실패한 경우가 있나?
7. 실패했을 때 복구 명령이나 되돌릴 경로가 있는가?

## Slop 방지 원칙

수정이나 구현 요청에서는 단순히 눈앞의 에러를 막는 근시안적 코딩을 피한다.

- 전체 맥락, 데이터 흐름, 호출 경로, 의존성을 먼저 파악한다.
- 증상만 가리는 땜질식 수정과 임시조치를 피한다.
- 가능하면 실패한 뒤 막는 방식보다 실패 경로 자체를 제거한다.
- 사후 검증으로만 안전을 보장하지 말고, 사전에 잘못된 상태가 만들어지지 않게 구조를 개선한다.
- 임시조치가 불가피하면 반드시 임시조치라고 표시하고, 후속 근본 해결안을 남긴다.

기본 판단 기준:

> “이 에러를 어떻게 막을까?”보다  
> “왜 이 에러가 생기는 길이 열려 있었나?”를 먼저 본다.

## 사용자 스타일에 맞춘 응답 방식

- 결론을 먼저 말한다.
- 완료조건은 길게 늘리지 말고 실행 가능한 항목으로 쓴다.
- 실패케이스는 실제로 일어날 법한 것만 쓴다.
- 검증방법은 명령/경로/기대 결과까지 구체적으로 쓴다.
- 확실하지 않은 보장은 "조건부"로 말한다.
