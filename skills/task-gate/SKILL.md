# Task Gate

사용자가 어떤 일을 시켰을 때 바로 실행하지 않고, 먼저 작업의 성공 기준과 실패 가능성을 명확히 고정하는 공통 운영 규칙이다.

## 적용 대상

다음 요청에는 반드시 적용한다.

- 코드 수정/구현/리팩터링
- 파일 생성/수정/삭제/이동
- 스케줄 등록/수정/삭제
- Claude/Codex 스킬 변경
- Obsidian 기록 자동화 변경
- 메모리 인프라, LanceDB, Wiki, Graphify, dump, wrap-up 변경
- 봇/훅/CLI/환경 설정 변경
- 사용자가 "되게 해줘", "고쳐줘", "수정해줘", "등록해줘", "연동해줘", "자동화해줘"라고 요청한 작업

단순 설명, 요약, 읽기, 상태 확인만 요청한 경우에는 생략해도 된다.

## 착수 전 필수 출력

작업을 실행하기 전에 아래 3가지를 먼저 제시한다.

```markdown
## 사용 순서
- 사용자가 어떤 순서로 행동하는지 (핵심 유저 플로우)
- 이 플로우가 중간에 끊기거나, 사용자에게 우회를 강요하지 않는지

## 완료조건
- 무엇이 되어야 완료인지
- 이번에 하는 것 / 이번에 안 하는 것
- 기존에 깨지면 안 되는 것
- 사용자가 기대하는 최종 상태

## 실패케이스
- 트리거가 안 걸리는 경우
- 잘못된 대상에 적용되는 경우
- 중복/누락/권한/경로/동기화 문제
- 환경 차이로 재현되지 않는 경우
- 사용자가 알아차리기 어려운 조용한 실패

## 검증방법
- 실행할 명령
- 확인할 파일/경로/로그
- 성공으로 볼 출력
- 실패 시 복구 방법
```

사용자가 이미 명확히 "진행", "응", "해줘"로 승인한 경우에는 실행해도 된다.

## 강도 조절 — 항상 켜되 작업 크기에 비례

게이트는 항상 작동하되 깊이를 작업 크기에 맞춘다. 매번 풀로 하면 무거워 안 쓰게 되므로 차등한다.

- **작음** (한 줄 수정, 단순 조회·확인): 게이트 생략 또는 한 줄 확인.
- **중간** (기능 하나 추가/수정): 사용 순서 + 완료조건 + 실패케이스만 짧게. 풀 명세는 생략.
- **큼** (새 앱/MVP, 멀티파일, 아키텍처 변경): 아래 명세 템플릿까지 작성.
- 같은 맥락의 반복 작업은 한 번 정한 기준을 재사용하고 다시 묻지 않는다.

## 큰 작업 명세 템플릿

큰 작업은 착수 전 아래 형태로 명세를 고정한 뒤 진행한다. 추상적 "잘 되면"이 아니라 **하나하나 확인 가능한 항목**으로 적는다.

```markdown
## goal
- 누구를 위해 / 무엇을 / 이것은 ~가 아니라 ~하는 도구다 (비목표 포함)

## 필수 기능
- (핵심 행동 목록, 사용 순서대로)

## 이번에 만들지 않을 것
- (제외 범위 — 스코프 크리프 차단)

## 데이터/구조 기준
- (다룰 데이터 형태·정렬·범위)

## 예외 처리
- 빈 상태 / 저장 실패 / 잘못된 입력 시 어떻게 알리나

## 완료 기준
- (검증 가능한 항목. 예: "1개 추가된다", "새로고침 후 데이터 남아있다", "삭제 전 확인창이 나온다")
```

## 인계 경계

task-gate는 **착수 전 기준 고정과 착수 후 검증**까지만 담당한다. 큰 작업의 실제 계획·실행은 superpowers(계획·발산)·omc(실행 위임)로 넘긴다. 게이트가 계획·실행까지 떠안지 않는다. 단순 작업에 superpowers/omc를 남용하지 않는다.

## 작업 후 필수 보고

완료를 주장하기 전에 검증을 실행하고 결과를 보고한다.

```markdown
## 검증결과
- 실행 명령:
- 결과:
- 통과:
- 실패/주의:
```

코드나 자동화 변경의 경우 테스트/빌드/조회 명령을 실제로 실행한다. 테스트가 없으면 파일 존재, 설정 반영, CLI 조회, 로그 확인 등 수동 검증 결과를 남긴다.

## 실패 모드 사고법

아래 질문으로 엣지케이스를 뽑는다.

1. 이 작업이 아예 실행되지 않으면 어떻게 알 수 있나?
2. 잘못된 대상에 적용되면 어떻게 알 수 있나?
3. 일부만 성공하면 어떤 증상이 나오나?
4. 중복 실행되면 문제가 생기나?
5. 다른 봇/세션/환경에서는 다르게 동작하나?
6. 사용자가 보기에는 성공처럼 보이지만 실제로 실패한 경우가 있나?
7. 실패했을 때 복구 명령이나 되돌릴 경로가 있는가?

## 사용자 스타일에 맞춘 응답 방식

- 결론을 먼저 말한다.
- 완료조건은 길게 늘리지 말고 실행 가능한 항목으로 쓴다.
- 실패케이스는 실제로 일어날 법한 것만 쓴다.
- 검증방법은 명령/경로/기대 결과까지 구체적으로 쓴다.
- 확실하지 않은 보장은 "조건부"로 말한다.
